## 修复及重复调用

1. 初次 D02 只得到文本结果：Markdown 内的 HTML `<img>` 未被解析。补充解析本地 HTML 图片，同时保留原文本块和证据位置；资产策略升级为 `assets-v3`。最终 15 张图片全部处理，不沿用“没有图片”的旧运行作为多模态通过结果。
2. 初次 D03 视觉 JSON 修复仍失败，修复请求出现输出长度截断。增加严格的 fenced JSON 对象解析，简化观察描述，并为评测视觉请求提供 8,192 输出 Token；普通抽取命令不改输出预算。
3. 首次 D04 复测发现 CMYK JPEG 无法直接保存为请求 PNG。只转换请求副本为 RGB，原始证据文件保持不变；单独复测 D04 后通过。证据区域导出也同步转换派生裁剪副本，已通过离线回归测试，不重新调用 API。
4. D02 后续复测发现观察置信度为字符串 `high`。Prompt 明确要求数值；无法校准的置信度保守记为 0，并将关联候选标记 `uncalibrated_visual_confidence`，沿对齐、规范化、事实合并传递，风险路由必须审核，不能因跨模态支持而消除保护。非法 bbox 降级整图证据并保留警告。
5. 已成功文本批次按模型/Prompt 指纹、文档哈希、Schema 和原始块缓存，复测共用原账本目录的缓存；OCR 复用必须核验 Provider、原文、资产 ID/哈希及已完成阶段。缓存不匹配立即失败，不使用答案替模型补齐结果。

D01 本轮执行一次；D02 执行三次（首次文本结果、失败多模态复测、最终复测）；D03 执行两次；D04 执行两次。重复运行及结构修复请求的实际用量均计入 409,277，不自动全量重跑。D05 没有重复调用。

主要质量问题：

- OneKE 框架中“系统包含组件”被部分候选表达成 `组件 developed_by OneKE`；组件归属不能证明开发者关系。
- 论文作者列表能支持 `authored_by`，不能直接当作 `系统/方法 developed_by 作者`。
- OneKE Logo 中名称可见，但 Logo 本身不能证明 OpenKG 是 Community 或 OneKE 是 SoftwareSystem；GitHub namespace 也不能单独证明开发者。
- D03 部分视觉候选使用 `p1 authored_by o1` 等模型占位名称，而非原文实体表面形式，不能计为正确实体事实或正确链接。
- MSPT 的缩写/全称关系被表达成 `proposes`，候选关系需要治理；部分可见能力描述产生 Schema 外关系/类型，目前尚未完成正式规范化。
- D05 的低置信 OCR 与人名拼写差异仍需复核；照片只能利用可读名牌和文字证据，不从人脸猜测身份。
- Q01 人工“同一人”意见保留，但身份依据不足仍不计分；Q02 保持不合并的定性案例；Q03 继续排除计分，原记录不删除。

这些问题没有被隐藏。五份状态均为等待审核，正式 Claim 数为 0，不宣称候选事实质量全部合格。
